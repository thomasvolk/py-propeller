# EP-2 · Concurrent Slide Consolidation — PRD

## Overview
Builds on EP-1. Because a pitch change affects an entire track rather than a single note, when two or
more slides on the same track sound at overlapping points in time, their pitch changes are merged
into one consistent sequence for the track instead of conflicting or duplicating. Each slide's own
notes still appear exactly as they would if it were the only slide sounding, so multiple simultaneous
slides can be composed without producing contradictory or redundant pitch movement.

**Confidence Level:** 94% — all three open questions are resolved: mismatched concurrent pitch-bend
values are rejected outright, only exact same-tick events are eligible for consolidation, and scope is
limited to Slide-generated events (manually-placed `PitchBend` notes keep today's collision behaviour).
No unresolved ambiguities remain that would block implementation.

---

## User Journeys

### UJ-1 · Composing two shape-matched concurrent slides
A composer writes two `Slide`s of identical tonal distance, duration, and step size in different lanes
of the same track (e.g. `Slide(C4, C5, steps=0.1) * 4` and `Slide(E4, E5, steps=0.1) * 4`, per the
briefing's example). Because both slides move through the same relative bend trajectory at the same
time, the composer expects the composition to render without a duplicate- or conflicting-pitch-bend
error, hearing both note lines glide together in parallel.

### UJ-2 · Composing slides on independent tracks
A composer writes overlapping slides on two different tracks. They expect each track's pitch bends to
be entirely unaffected by the other track's slides, regardless of how the timing lines up.

### UJ-3 · Composing shape-mismatched concurrent slides
A composer writes two `Slide`s in different lanes of the same track that overlap in time but differ in
tonal distance or duration (e.g. one spans an octave, the other a fifth). At the tick where their
pitch-bend events collide, the required bend values differ. The composer expects a clear validation
error rather than the composition silently rendering with one slide's intended glide dropped or
blended away.

### UJ-4 · Composing slides whose bend events don't align exactly
A composer writes two `Slide`s in the same track whose individual pitch-bend events happen to land at
different, non-matching ticks (even though the slides overlap in time overall). They expect every
event from both slides to appear in the output, interleaved in time order, with no merging attempted
between non-matching ticks.

## Functional Requirements

| ID | Requirement |
|----|-------------|
| F-1 | When two or more Slides in different lanes of the same track produce pitch-bend events at the same tick with the same pitch-bend value, the output contains a single pitch-bend event at that tick for the track, not one per slide. |
| F-2 | Each Slide's own Note events appear in the output exactly as they would if that Slide were the only one present in the track — consolidation affects only pitch-bend events, never note placement. |
| F-3 | Pitch-bend consolidation is scoped per track; Slides on different tracks never influence each other's pitch-bend output, regardless of timing overlap. |
| F-4 | When two or more Slides in the same track produce pitch-bend events at the same tick with different values, the composition is rejected with a validation error rather than being silently rendered. |
| F-5 | Pitch-bend events from concurrent Slides are only merged when they land on the exact same tick; events at non-matching ticks are preserved as separate entries in time order, with no merging or tolerance-based grouping. |
| F-6 | Consolidation applies only to pitch-bend events generated by Slides; a Slide's pitch-bend event colliding with a manually-placed `PitchBend` note at the same tick is not consolidated and remains a validation error, consistent with existing behaviour. |

---

## Non-Functional Requirements

| ID | Requirement |
|----|-------------|
| NF-1 | Consolidation is deterministic — the same set of concurrent Slides on a track always produces the same consolidated pitch-bend sequence. |

## Acceptance Criteria

| ID | Given | When | Then |
|----|-------|------|------|
| AC-1 | Two Slides in different lanes of the same track that produce identical pitch-bend values at the same ticks (e.g. `Slide(C4, C5, steps=0.1) * 4` and `Slide(E4, E5, steps=0.1) * 4` in the same track) | the composition is serialized | the output contains exactly one pitch-bend event per tick for that track, not two |
| AC-2 | The same two Slides from AC-1 | the composition is serialized | each Slide's Note events appear in the output unchanged from how they would appear if that Slide were the only one in the track |
| AC-3 | Slides on two different tracks with overlapping timing | the composition is serialized | each track's pitch-bend output reflects only the Slides on that same track |
| AC-4 | Two Slides on the same track whose pitch-bend events fall at the same tick but specify different values (e.g. differing tonal distance or duration) | the composition is serialized | a validation error is raised and no output is produced |
| AC-5 | Two Slides on the same track whose pitch-bend events fall at non-matching ticks | the composition is serialized | all events from both Slides appear in the output as separate entries, sorted in time order, with none merged |
| AC-6 | A Slide whose pitch-bend event falls at the same tick as a manually-placed `PitchBend` note in another lane of the same track | the composition is serialized | a validation error is raised, the same as when two plain lanes collide today |
